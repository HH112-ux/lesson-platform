## 2. 背景与目标

订单是交易链路的唯一入口，重复提交、重复点击与网络重试都会造成重复建单，进而产生重复支付与重复权益。本条目确立下单的服务端权威边界：用户身份只来自网关注入的 `X-User-Id`，金额只由服务端按课程审核确认价与优惠券计算，幂等由「用户 + 幂等键」唯一约束兜底。完成后，同一用户的同一次购买意图无论重放多少次，都只对应一笔订单。

## 3. 范围

### 3.1 包含

- `POST /api/v1/orders` 创建订单（首版一次下单仅一门课程）。
- 幂等键校验与 `uk_idempotency(user_id, idempotency_key)` 唯一约束兜底。
- 下单前的课程可售校验、已购校验、优惠券核销（券规则本身见 SPEC-TRADE-003）。
- 由服务端计算 `total_amount`、`discount_amount`、`pay_amount`。

### 3.2 范围外

- 应付为 0 时的即时完成与权益发放，见 SPEC-TRADE-002。
- 支付渠道固定与小程序下单拒绝，见 SPEC-TRADE-004。
- 权益发放的最终一致与重复投递吸收，见 SPEC-LEARN-001。
- 购物车结算与合并下单，本期不做。

## 4. 用户场景

| 编号 | 类型 | 场景 | 期望结果 |
|---|---|---|---|
| S-1 | 正常 | 学员在 Web 课程详情页点击购买，前端生成一个幂等键并提交一次 | 返回订单号，状态为待支付，`payAmount` 等于课程最终价减优惠 |
| S-2 | 正常 | 前端因超时重试，使用同一幂等键再次提交 | 返回与首次完全相同的订单号与金额，订单表仍只有一条记录 |
| S-3 | 边界 | 两个请求并发携带同一幂等键提交 | 两个响应指向同一订单号，数据库只落一条 `trade_order` |
| S-4 | 异常 | 学员已持有该课程有效权益再次下单 | 返回 `61002`，不创建订单 |
| S-5 | 异常 | 请求体伪造 `userId` 或 `price` 字段 | 用户以 `X-User-Id` 为准，金额以服务端计算为准，伪造字段不生效 |

## 5. 验收标准

- AC-1：同一用户使用同一 `idempotencyKey` 重复或并发提交下单请求时，数据库只产生一条 `trade_order`，且所有成功响应返回同一个 `orderNo`。
- AC-2：下单前若该用户在 `user_entitlement` 存在 `user_id + course_id` 的有效权益，接口返回 `61002` 并且不写入任何订单记录。
- AC-3：课程当前状态不为已上架（`status != 2`）时下单返回 `61001`，不创建订单，也不核销优惠券。
- AC-4：下单请求体不接受价格字段，客户端传入 `price`、`payAmount` 或 `totalAmount` 任一时，订单金额仍等于服务端按课程最终价与优惠券计算的结果。

## 6. 边界与异常

| 编号 | 触发条件 | 系统表现 | 关联 AC |
|---|---|---|---|
| E-1 | 未携带或携带无效凭证 | 网关拦截并返回 `40101`，请求不进入 trade-service | AC-1 |
| E-2 | `courseId` 为空或非数字 | 返回 `40001`，不落单 | AC-3 |
| E-3 | `idempotencyKey` 缺失、为空或超过 64 字符 | 返回 `40001`，不落单 | AC-1 |
| E-4 | 课程不存在或已逻辑删除 | 返回 `40401`，不落单 | AC-3 |
| E-5 | 优惠券不可用（不属于本人、已使用、过期、不满足门槛） | 返回 `62003`，整单回滚，订单与券状态均不变化 | AC-4 |
| E-6 | 同一幂等键第二次提交时课程已售罄或已下架 | 仍按幂等返回原订单，不因当前课程状态改变已建订单 | AC-1 |
| E-7 | 同一用户同一幂等键但 `courseId` 不同 | 按未决问题 Q-2 的结论执行 | AC-1 |
