## 2. 背景与目标

支付宝异步通知是订单从待支付变为已支付的唯一依据，且会按固定间隔重试多次。回调处理必须同时满足三件事：拒绝伪造、重复通知不重复发货、异常订单（已关闭、不存在）有确定处置。本条目冻结这三种情形的落库与应答，避免「钱收了、订单还关着」或「重复回调发放两次权益」。

## 3. 范围

### 3.1 包含

- `POST /api/v1/payments/alipay/notify` 的验签、参数校验与纯文本应答。
- 支付记录、订单状态、权益发放触发（写 outbox）在同一事务内的一致更新。
- 重复通知、订单已支付、订单已关闭、订单不存在四类分支的处置。

### 3.2 范围外

- 发起支付与重付约束，见 SPEC-TRADE-004。
- 权益实际落库与重复投递吸收，见 SPEC-LEARN-001。
- 已关闭订单收到款项后的退款流程，见 SPEC-TRADE-008 与 SPEC-TRADE-009。
- 对账账单核对，见 SPEC-TRADE-014。

## 4. 用户场景

| 编号 | 类型 | 场景 | 期望结果 |
|---|---|---|---|
| S-1 | 正常 | 支付宝对一笔待支付订单发送首次成功通知 | 支付记录成功、订单已支付、outbox 写入待投递权益，应答 `success` |
| S-2 | 正常 | 支付宝因未及时收到应答再次推送同一通知 | 应答 `success`，支付记录与订单不产生第二次变更 |
| S-3 | 边界 | 通知到达时订单已是已支付（另一条通知先到） | 应答 `success`，不重复写 outbox |
| S-4 | 异常 | 签名不合法或通知金额与 `pay_amount` 不一致 | 应答 `failure`，不改变订单与支付记录状态，写入告警日志 |
| S-5 | 异常 | 订单在通知到达前已被超时关闭 | 落库留痕并标记为待退款补偿，应答 `success` 以停止渠道重试 |

## 5. 验收标准

- AC-1：支付宝通知的 RSA2 验签失败，或通知中的 `total_amount` 与 `trade_order.pay_amount` 不一致时，接口返回 `failure`，订单状态、支付记录成功态与权益 outbox 均不发生任何写入。
- AC-2：同一 `channel_trade_no` 的通知重复到达时，接口返回 `success`，`payment_record` 只有一条成功记录，`entitlement_outbox` 不新增记录。
- AC-3：通知到达时 `trade_order.status` 已为 1 已支付，接口返回 `success` 且不重复更新 `paid_at`、不重复写入 outbox。
- AC-4：通知到达时 `trade_order.status` 为 3 已关闭，服务端保存支付成功事实与渠道交易号，订单状态保持 3，并写入待退款补偿标记，接口返回 `success`。
- AC-5：通知中的 `out_trade_no` 在 `trade_order` 中不存在时，接口返回 `failure`，不创建订单或支付记录，写入告警。
- AC-6：支付宝异步通知中的 `app_id` 必须等于本平台配置的商户应用 ID；不一致时接口返回 `failure`，不写入支付成功记录、不改变订单状态、不写 `entitlement_outbox`。

> 说明：渠道验签已落地（`e2e800b`），Mock 渠道仍保留用于联调。

## 6. 边界与异常

| 编号 | 触发条件 | 系统表现 | 关联 AC |
|---|---|---|---|
| E-1 | 支付渠道密钥或支付宝公钥未配置 | 返回 `failure`，不伪造成功（对应 `50205` 口径） | AC-1 |
| E-2 | 通知中的 `app_id` 不是本应用 | 返回 `failure`，不落库 | AC-6 |
| E-3 | 通知重复且金额与首次一致 | 幂等成功，无额外写入 | AC-2 |
| E-4 | 同一 `out_trade_no` 出现两个不同 `trade_no` | 保留首个成功记录，返回 `failure` 并告警人工核对 | AC-2 |
| E-5 | 通知在事务提交前到达第二次 | 依赖 `uk_channel_trade` 唯一约束串行化，后到者按重复通知处理 | AC-2 |
| E-6 | 订单已关闭且已产生退款单 | 只留痕，不重复创建退款单，交由退款审核承接 | AC-4 |
